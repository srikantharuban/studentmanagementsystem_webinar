## Implementation Notes (Source Analysis)

> These observations were extracted from [`static/login.html`](../../static/login.html) and [`static/app.js`](../../static/app.js) and inform the expected results below.

- Authentication is **entirely client-side** — credentials are hardcoded in `login.html` inside the `USERS` object. There is no API call.
- Username is **trimmed and lowercased** before lookup: `value.trim().toLowerCase()`.
- Password is **case-sensitive** with no transformation.
- On success: sets `sms_auth=true`, `sms_user`, `sms_role`, `sms_label` in `sessionStorage`, then redirects to `/ui/`.
- On failure: shows inline error "⚠ Invalid username or password. Please try again.", clears and focuses the password field. **No lockout mechanism exists.**
- On logout: only removes `sms_auth` and `sms_user` — `sms_role` and `sms_label` are **not removed** (potential residual data).
- Auth guard in `app.js` checks `sessionStorage.getItem('sms_auth') !== 'true'` on `DOMContentLoaded` and redirects to `/ui/login.html` if false.
- Password field uses `type="password"` (masked in UI).
- Quick-fill: clicking a row in the access table auto-fills credentials.

## Assumptions

| # | Assumption |
|---|---|
| A1 | No account lockout threshold is defined — test confirms no lockout occurs after N failures (flag as a gap). |
| A2 | No session timeout is implemented — the session persists until the tab/browser is closed or logout is clicked. |
| A3 | "Access Restricted" page content is the observable outcome for unauthorized navigation; no HTTP 403 is issued (client-side guard only). |
| A4 | `sms_role` and `sms_label` not being cleared on logout is treated as a gap to flag, not confirmed behavior. |

## Identified Gaps / Risk Flags

| # | Gap | Severity | Recommendation |
|---|---|---|---|
| GAP-01 | **No brute-force protection** — no lockout, rate-limit, captcha, or delay after repeated failures | High | Implement server-side rate limiting or lockout for production use |
| GAP-02 | **Logout leaves residual session keys** — `sms_role` and `sms_label` are not removed from sessionStorage | Medium | Add `sessionStorage.removeItem('sms_role')` and `sessionStorage.removeItem('sms_label')` to the logout function |
| GAP-03 | **Hardcoded credentials in client-side JS** — all 4 passwords are visible in page source | Critical | Move authentication to a server-side endpoint for any non-demo deployment |
| GAP-04 | **Auth guard bypassable via DevTools** — setting `sms_auth=true` manually grants full access | Critical | Implement server-side session validation (e.g. signed JWT or server session cookie) |
| GAP-05 | **No session timeout** — authenticated session persists indefinitely within the tab | Medium | Implement an inactivity timeout for production use |
| GAP-06 | **API endpoints have no authentication middleware** — all REST endpoints are accessible without login | Critical | Add authentication middleware to FastAPI routes for production use |
